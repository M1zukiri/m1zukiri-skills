# 页面类型与坐标来源

本文件说明**为什么不能只保留一条坐标路径**，以及各类页面的实测表现。

## 分类依据

按**页面是怎么产生的**分，而不是按项目或框架分：

| 类型 | 页面怎么来 | 源码在哪 | 坐标方案 | 实测 |
|---|---|---|---|---|
| A 代码生成静态页 | 生成器用 f-string 逐段拼 HTML | 生成器脚本 | 生成器注入 `data-src` | 覆盖 100%、准确率 100% |
| B 模板组装静态页 | 组装脚本把「模板 + 前端逻辑 + 数据」拼成单文件 | 模板文件、前端 JS | 离线反查 | 静态部分覆盖 100%、准确率 96–98%；运行时生成的 DOM 覆盖 0% |
| C 前端框架应用 | 构建工具打包，DOM 运行时渲染 | 组件源码 | 待验证 | — |
| D 外部网页存档 | 抓取他人的网页保存 | 无 | 不适用 | — |

**分类的根源是 A 与 B 的差异，不是「有没有生成器文件」。** 这两类的字面量分布完全不同：

- **A 类**：页面元素由代码逻辑生成，源码里是 f-string 模板串。元素文本（尤其动态部分）在源码里找不到对应字面量。
- **B 类**：页面的静态结构直接抄自模板文件，元素与模板行近乎一一对应。

因此 A 类必须靠生成器自报来源，B 类靠反查就够——**两条路径是客观需要，不是设计冗余**。`make_annotator.py` 自动判定（页面有 `data-src` 用注入，没有则反查），用户和 agent 都不需要预先分类。

## A 类：代码生成静态页

**特征**：项目里有生成器脚本 + 结构化的输入（脚本、结果 JSON、README）。页面的每个区块都由生成器的某个函数渲染。

**为什么反查效果差**：元素文本经拼接后与源码字面量对不上。同一份页面用反查只有 **76.8%** 覆盖（动态拼接的项目名、脚本名、`×N` 徽标在源码里根本没有字面量）。

**方案**：让生成器在渲染时写出自己的坐标。生成器知道每段 HTML 从何而来，不存在猜测。

**坐标形式**：项目源码用 `文件:行号`；生成器自己的文案（标签、图注、章节标题）用 `gen:<锚点>`。

**内联 helper 的坑**：如果生成器会内联其他模块的函数（例如把 `_common.py` 的调用点展开进主脚本的流程图），**行号必须连同定义文件一起传递**。只带行号会把 helper 里的行号贴到主脚本名下——页面上看似合理，实际指向错误的文件。实测中这类错误占全部坐标的 15%。

## B 类：模板组装静态页

**特征**：页面是同目录或 `src/` 下的「组装脚本 + 模板文件 + 前端逻辑 + 数据」拼成的单文件。

**为什么反查效果好**：模板文件里的标签与页面的静态结构一一对应，前端 JS 里则是动态文本的字面量。

**关键：源码集合必须齐全。** 只喂组装脚本时，实测反查命中 **52/562**；补上模板文件与前端逻辑后达到 **562/562**。组装脚本只负责把几块拼起来，页面的绝大部分字面量在模板和前端逻辑里。

`make_annotator.py` 默认扫描页面同目录与 `src/` 子目录，若结果不理想应显式补 `--source`。

**实测准确率**（逐条回读源码行核对，两个页面）：

| 置信度 | 页面 1 | 页面 2 |
|---|---|---|
| high（文本字面量） | 97.5% | 97.6% |
| medium（容器首叶文本 / 动态 id 前缀） | 91.5% | 89.9% |
| low（class 名） | 100% | 100% |

未命中项经逐条核对，**全部是核对脚本对短词（两三个字的小标题）的阈值所致，不是索引错误**。

**祖先继承约占 39%**：表格单元格与动态模板片段自身没有字面量，只能继承容器的位置。它回答的是「该改哪个函数」，不是「该改哪一行」——这对表格类元素通常足够（改结构要去渲染表格的函数），但改单个数值要去数据层。

### B 类的边界：运行时生成的 DOM

上面那组 100% 只对**静态 HTML 里已经存在的元素**成立。B 类里有一支是**应用型单文件页面**——整屏由 JS 渲染，DOM 在运行时才长出来。

实测（一个 992 KB 的应用型单文件页面）：

| 指标 | 数值 |
|---|---|
| 浏览器实际 DOM 元素 | 338 |
| 离线反查索引键 | 157（46%） |
| 157 个键能匹配到真实 DOM | **157 / 157** |
| 空态可见元素中有坐标 | 62 / 62 |
| **弹窗打开后，弹窗内可见元素中有坐标** | **0 / 43** |

根因不是配置、也不是源码集合没喂够：`index_elements.py` 用静态解析器读 HTML **文件**，而该页面的弹窗由前端模块在运行时 `createElement` + `innerHTML` 创建——在 `index.html` 里 grep 弹窗相关 id 是**零匹配**，静态文件里根本没有这些节点，索引里自然没有条目。

**用户最想改的往往正是这些运行时区域。** 第二轮真实使用中，6 条批注有 3 条落在同一个运行时弹窗内，全部没有坐标。

补救不靠扩大索引——运行时 DOM 的 CSS 路径与静态树对不上，强行匹配会产出**看似合理实则错误**的位置，比没有坐标更危险。正确做法是用批注自身保留的线索反查：`cls` → `cssPath` → `text`。同一轮三条无坐标批注**全部**借此定位成功（分别命中前端模块里的三处模板字符串与一处容器宽度定义）。

## C 类：前端框架应用

**特征**：有构建工具配置（如 `vite.config.ts`）、依赖清单、`src/` 下的组件源码；`index.html` 只是几百字节的入口壳。

**当前状态**：未验证。理论上可以把组件源码（`.tsx`/`.vue`/`.js`）作为 `--source` 让离线反查命中 JSX 里的中文字面量，但运行时 DOM 与组件结构的对应关系随框架、条件渲染、列表 key 而变，需要实测才能给结论。

**建议**：先用本 skill 跑一次离线反查，看反查覆盖率与 `lineText` 是否指对地方，再决定是否需要进一步的方案。

## D 类：外部网页存档

**特征**：抓取或另存下来的他人网页（研究资料、论坛、数据页）。

**处理**：**不适用本 skill**。这类页面没有「源码」可改——即使标出元素位置，也无处修改。若用户想改的是这类页面的显示，正确做法是写用户样式或另建页面，而不是批注。

生成副本本身能跑（运行时与页面无关），但导出的坐标会为空或指向无意义的位置。

## 混合情况

同一项目可能同时包含多类页面。例如一个仿真项目既有生成器产出的展示页（A 类），也有手工写的说明页。**逐页面判定，不必整个项目归一类**——`make_annotator.py` 每次只看目标页面。

## 结论

- 判定「哪一类」的依据是**页面自身的特征**（有没有 `data-src`、有没有配套源码），不是项目类型或使用的框架。
- 两条路径（注入 / 反查）**都要保留**：A 类注入才准，B 类反查就够，互不替代。
- 用户与 agent **不需要手动分类**——脚本自动判定，并在输出里说明用了哪条路径、覆盖多少元素。
