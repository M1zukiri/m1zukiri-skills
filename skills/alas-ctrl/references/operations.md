# 人工操作记录库

## 这个文件是干什么的

用户希望在「需要人工介入」的时刻把操作交给我执行，并要求**记录触发条件与具体做法**。
随着记录累积，这些判断可以逐步变成自动流程，最终替代用户手动操作。

所以每条记录必须回答四件事：

1. **怎么知道需要动手**（可观测的触发信号）
2. **为什么这是人工场景**（ALAS 为什么自己不处理）
3. **具体怎么做**（可复现的命令序列）
4. **怎么确认成功**（验证信号）

## 记录格式

```markdown
## OP-NNN <一句话标题>

- **触发信号**：<在 status / 日志 / scheduler.out.log 里能看到什么>
- **判断**：<为什么 ALAS 不会自愈>
- **做法**：<编号步骤，含具体命令>
- **验证**：<成功后的可观测状态>
- **能否自动化**：<是 / 否 / 部分 + 缺什么>
- **首次记录**：<YYYY-MM-DD>　**复现次数**：<n>
```

新增记录时追加到文件末尾，编号递增。若同类场景再次发生，不要新开编号，把「复现次数」加一，
并把新观察到的变体补进「判断」。

## 记录前的安全边界

- 操作前先确认没有 ALAS 实例在跑（`status` 为 `DOWN` 或 `CONFLICT` 时不要动）。
- ALAS 运行时**禁止** `adb shell input`——会与 MaaTouch 抢注入。
- 任何消耗资源、不可逆的操作（兑换、退役、分解、抽卡）一律先问用户。

## OP-001 启动失败：`Game page unknown`（游戏停在未识别弹窗）

- **触发信号**：
  - `alasctl start` 报存活，但一分钟后 `status` 变 `DOWN`；
  - `state/scheduler.out.log` 出现
    `Starting from current page is not supported` 与 `CRITICAL Game page unknown`；
  - 日志里已有 `WARNING Saving error: ./log/error/<ms>`。
- **判断**：游戏停在一个 ALAS 未收录的界面（本例是舰队商店的「确认兑换该商品」弹窗，
  由上一次任务被强行中断留下）。ALAS 启动时 `is_first_task` 会**跳过 `Restart`**，
  所以它不会自己重启游戏从登录页开始，而是直接尝试从当前页继续，识别失败即退出。
- **做法**：
  1. 确认没有 ALAS 在跑：`alasctl status`。
  2. 截图看卡在哪：`adb -s <serial> exec-out screencap -p > tmp.png`，读图判断界面性质。
  3. 若是「确认/提示」类弹窗，点弹窗里的**取消**按钮关闭：
     `adb -s <serial> shell input tap <x> <y>`（1280×720 坐标系）。
  4. 再确认一次截图，确保回到了 ALAS 支持列表内的常规页面（右上角有 HOME 按钮）。
  5. `alasctl start`。
- **验证**：`status` 显示 `RUNNING`，日志出现 `Scheduler: Start task`。
- **能否自动化**：部分。可以自动化的是「启动后 60 秒仍未出现 `Start task` 就截图并告警」；
  缺的是弹窗模板匹配——要判断点哪个按钮，仍需看图。
- **首次记录**：2026-11-16　**复现次数**：1
- **教训**：`stop --force` 会打断任务并留下未关闭的弹窗，下次启动就卡这里。
  能用默认 `stop`（等任务间隙）就不要用 `--force`。
