# modes/research

**适用**：技术选型、可行性评估、文献或资料综述、现状盘点、方案对比。
**不适用**：以产出可运行代码或可运行服务为主的项目。

**来源**：全局基线的「准确性与推理效率」、`m1zukiri-profiles-md/reference/` 下 62 份调研报告的实际形态、
`m1zukiri-profiles-md/projects/daily-news/` 的采集-报告流水线。

<!-- anchor: source-tiering -->
## 来源分层

每条结论标注证据层级，不要混：

| 层级 | 含义 |
| --- | --- |
| 单篇实证 | 一个来源的直接数据或原文 |
| 综述共识 | 多个独立来源收敛到的结论 |
| 本人推断 | 从结构推出来、没有直接证据 |

推断必须显式标注「推断，无来源确认」。

<!-- anchor: conclusion-strength -->
## 结论强度

- 主张强度不得超过证据强度。删掉夸张词后如果剩不下信息，重写而不是加词。
- 单一来源不构成结论。要么再找一个独立来源，要么明确写「单一来源，未交叉验证」。
- 「首次」「唯一」「突破」「显著」这类词必须有引用或数据支撑，并注明来源层级。
- 数据陈述给精确值，不给感叹号；近似值写「约 N 倍」而不是「翻倍」。

<!-- anchor: currency -->
## 时效

- 每个来源给日期与获取时间。技术结论超过一定时限要重新验证，不要沿用旧结论。
- 「当前」「最新」这类相对词，必须换成可定位的版本号或日期。

<!-- anchor: structure-delivery -->
## 结构与交付

- 结论先行：先给可执行的判断，再给证据链。
- 分节写：结论 / 证据（带出处）/ 待定（证据不足、无法核实的事项）。
- 不确定的进「待定」，不猜、不用相近结论顶替。
- 过程记录（试过哪些路径、怎么排除的）与结论分开写；被否决的方案要记录**为什么**否决，
  否则下一个人会重走一遍。
