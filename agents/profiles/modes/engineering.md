# modes/engineering

**适用**：以写代码、改代码、跑构建、做数值验证为主要活动的项目。
**不适用**：纯写作、纯调研、纯值守运维（各自有 mode）。

<!-- anchor: kickoff -->
## 开工前

- 读项目 `AGENTS.md` 的坑，读 `NOTES.md` 的当前状态与待决事项。**不知道上次做到哪里就不要动手。**
- 先确认这次改动的验收方式（测试、数值对齐、手工验收步骤），写进计划再动手。

<!-- anchor: coding-conventions -->
## 编码约定

- 命名与文件组织遵循项目既有约定，不引入第二套风格。
- 注释说明意图与约束，不复述代码；保留与其他实现语言对照所需的路径与行号。
- 边界条件、空值、越界、精度与索引转换按项目契约处理，不凭经验猜。
- 错误处理只覆盖真实可能发生的场景；不静默吞错。
- 与参考实现对照时保持可追溯性：形参顺序、索引基准、单位与量纲必须明确。

<!-- anchor: build-deps -->
## 构建与依赖

- 构建命令、产物路径、运行入口写入文档；新增依赖前评估是否必要。
- 保持构建可复现：固定工具链与依赖版本，避免本机隐式依赖。
- 对外接口（CLI、ABI、API、配置文件）的契约显式记录；破坏性变更先确认。

<!-- anchor: baseline-first -->
## 先取基线再改

改之前先让现有验证跑通一次，记录结果。没跑过基线就动手，出问题时分不清是改坏了还是本来就有问题。

基线包括：构建是否通过、测试是否全绿、关键命令是否产出预期输出。三者取该项目实际有的。

<!-- anchor: tests-acceptance -->
## 测试与验收

- 先写能复现问题的测试，再改实现。
- 有参考实现时做数值对齐，给出明确阈值（如偏差 ≤ 0.01 dB）；验收标准写进文档。
- 测试覆盖真实边界，不做只验证 happy path 的形式测试。
- 提交前跑完整相关测试；失败不许绕过或跳过。

<!-- anchor: same-check-after -->
## 用同一条验证证明改动

改完必须跑**与基线完全相同**的那条验证。换一条更宽松的检查、或只做肉眼确认，都不算验证通过。

改动声称解决的问题，要能被一条可执行的检查复现出来：改前失败、改后通过。做不到就先别改。

<!-- anchor: debugging -->
## 调试与排查

- 先证据后猜测：用日志、计时、dump、profiler 定位，不靠直觉改代码。
- 长任务保留执行时间与中间结果，便于断点恢复。
- 排查顺序写进文档：现象 → 缩小范围 → 验证假设 → 修复 → 回归。
- 只读边界：对监控、配置、外部服务默认只读；写入必须经明确授权，并在独立仓库追踪。
- 不用 UI 推断内部状态；直接读运行时的状态、配置或接口返回值。

<!-- anchor: backup-before-change -->
## 改动前备份

- 改核心文件（入口、协议、配置解析、构建脚本）前备份，命名 `<原文件名>.bak-YYYYMMDD-HHMM`。
  **同名后缀直接覆盖，不累积多份**；备份是回滚手段，不进交付物、不进 git。

<!-- anchor: wrap-up -->
## 收尾协议

每完成一个**可验证节点**（不是会话结束），按顺序做：

1. 跑验证，记下结论：通过/失败、关键数值、耗时。
2. 更新项目 `NOTES.md` 的进度节：日期、完成了什么、验证结果、下一步。
3. 新踩到的坑追加进项目 `AGENTS.md`，按日期标注，**不要只留在会话里**。
4. 判断这条坑是否对所有项目成立；成立就提议上移到 `agents/profiles/`，再 `sync` 到各项目。

<!-- anchor: diff-selfcheck -->
## diff 自查

提交前逐行看一遍 diff，每行问「这行对应哪个需求」。答不上来的行删掉。

特别检查：有没有顺手改的相邻格式、有没有被改动的死代码、有没有调试残留。

<!-- anchor: version-commit -->
## 版本与提交

按全局基线的「版本与 Git」章节执行。项目若有更严格的版本规则（例如 git tag 是唯一权威，
`AGENTS.md` 里的版本号只是快照），以项目 `AGENTS.md` 为准。
